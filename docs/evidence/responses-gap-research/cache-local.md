## Cache evidence and interpretation

The historical `features-cache-20260920T155342069944Z.json` report contains two successful calls with only 20 input tokens each and explicit `cached_tokens: 0`; its input is far below the public documented prefix-sizing threshold, so it does not establish Codex OAuth cache eligibility. See that report lines 9–29 and the earlier summary in `local-failures.md` lines 19–23.

The seven-call probe in `native-probes.md` lines 9–12 and `native-probes.json` lines 82–96 reused one 1,800-word request body and one key twice. Both calls returned HTTP 200 and explicit `cached_tokens: 0`; its semantic capture omitted `input_tokens`, so it could not verify the actual token-count precondition. The probe author confirmed that these requests used Python `urllib` with only Authorization, Content-Type, and Accept. They neither set nor captured `session-id`. The cache result was therefore a no-session-header baseline, not a test of the official Codex cache-affinity wire format.

The subsequent four-call experiment in `cache-ab-20260920.json` captured the sanitized SDK request headers and completed usage. All four calls had the same request-body hash and 1,822 input tokens. With no `session-id`, two responses reported `cached_tokens: 0`. With `session-id` set to the same value as the body `prompt_cache_key`, the first response reported 0 and the second reported 1,664 cached tokens of 1,822 input tokens. All four returned HTTP 200; the report’s call classes are at lines 84–87 and usage values at lines 51–77. This is a strong controlled result for session affinity with a warmed repeated prefix. It is not an A-B-A reversal, and the evidence is client-side SDK capture plus returned usage rather than a direct capture at ChatGPT's network edge.

## Wire path and usage reporting

Pinned local Codex source explains the missing field: `upstream/codex-132c2be239ecbc1f2a9bb22d9210fefe887986a5/codex-rs/core/src/client.rs:575-582` says ChatGPT derives Responses cache affinity from the `session-id` header and uses `prompt_cache_key` as the root session identity. The request builder places `prompt_cache_key` in JSON at `client.rs:959-980`, and creates both `session-id` and `thread-id` headers at `client.rs:1308-1312`; exact hyphenated header serialization is in `codex-api/src/requests/headers.rs:5-12`.

Before this fix, `src/server/response-adapter.ts:7-13` used a loose request schema, and `:45-57` spread parsed fields back into the JSON body, so `prompt_cache_key` survived translation. `src/server/upstream.ts:27-39` forwards incoming `session-id`; `:89-103` limits this adapter to minimal-mode `POST /v1/responses`. It did not derive a header from the body key. Standard SDK calls and the seven-call `urllib` runner did not send this Codex-specific header.

There is no local `cached_tokens` defaulting path. The Python SDK model used by the feature runner requires `InputTokensDetails.cached_tokens` (`~/.cache/uv/environments-v2/cache-probe-de5a0447b00a7010/lib/python3.14/site-packages/openai/types/responses/response_usage.py:8-18`); `test_features.py:92-97` reads that field directly. The recent native probe also recorded that the field was present in both responses. On the gateway, `response-stream-adapter.ts:55-79` only replaces an absent/empty `output` while spreading the original terminal event and response; the usage object remains intact. `response-adapter.ts:68-104` likewise returns the upstream final response with its fields intact. The fixture in `tests/fixtures/proxy-cache.test.ts:187-205` checks that input/cache counters survive the streamed terminal response.

Competitor source is consistent with treating cache identity as routing metadata: Sub2API uses `prompt_cache_key` as a session-id fallback before its WebSocket route (`sub2api-codexlb.md:42-49`), while codex-lb distinguishes soft cache affinity from hard continuation ownership (`:51-57`, `:128-132`). Those implementations do not independently establish a hit; the local four-call A/B supplies that evidence.

## Hypotheses resolved and remaining limits

1. **Missing session affinity — strongly supported.** The same measured body/key produced no observed hit without `session-id`; a repeated treatment with matching `session-id` produced a 1,664-token hit. The local proxy now derives that header only for a representable body key, only in minimal Responses mode, and only when the caller did not send the header.
2. **Ineligible or unwarmed prefix — earlier ambiguity, with timing/warm-up still not excluded by the A/B order.** The old test had 20 input tokens. The later A/B measured 1,822 tokens; its first treatment call remained cold and the next treatment call hit, consistent with a warm-up step.
3. **Reporting default or proxy counter rewrite — not supported.** The successful A/B artifact records actual input usage and explicit cached-token values; local response handling preserves terminal usage. Earlier reports still lack request-header evidence and one lacks input-token evidence, which is an observability omission rather than proof of an absent cache.

The adapter declares `prompt_cache_key` as an optional unknown in its loose schema and leaves every body value untouched. It derives no header for absent, null, non-string, empty, whitespace-padded, CR/LF, or Unicode values; a candidate must be a nonempty printable-ASCII string unchanged by trim. There is no arbitrary length cap. Explicit incoming `session-id` always wins. A fixture also proves a valid key on another POST route does not gain the header and keeps its body byte-for-byte. No synthetic usage, random key, global cache state, or upstream call was added by the implementation.
