# CLIProxyAPI competitor audit (and Plus)

Audited code is pinned to [`router-for-me/CLIProxyAPI` `09a29bd345bc44c473abe7fd07859e32df2ea543`](https://github.com/router-for-me/CLIProxyAPI/commit/09a29bd345bc44c473abe7fd07859e32df2ea543), the Sep 10 snapshot used for source-level claims below. This is a large, actively released Go proxy (GitHub showed roughly 52.5k stars, 7.9k forks, and an update on Sep 19; latest release page showed v7.3.2 on Sep 14). These are maturity signals, not evidence that every Responses feature works. The Sep 10 SHA predates that latest release. [Repo activity](https://github.com/router-for-me/CLIProxyAPI/commits/main), [current releases](https://github.com/router-for-me/CLIProxyAPI/releases), [org repository metadata](https://github.com/router-for-me).

The local comparison is [our Responses test result](../responses-implementation/RESULTAT.md): HTTP `previous_response_id` was rejected; two-turn native WS continuation passed; response retrieval/delete/cancel/input-items, background, input-token count, conversations, and compact lifecycle probes got 400/403/404; image input was accepted but returned the wrong color; the encrypted reasoning item was not emitted despite `include`; prompt-cache counters did not demonstrate a hit. Keep these as observed outcomes for this run, not universal OpenAI behavior.

## What the proxy actually does

| Gap | CLIProxyAPI evidence | What that means for our failure |
| --- | --- | --- |
| HTTP continuation | The Codex HTTP executor takes the downstream payload (`req.Payload`), translates/normalizes it, then explicitly deletes `previous_response_id` before POSTing `/responses`. It sets `stream:true` and also deletes `generate`, `prompt_cache_retention`, `safety_identifier`, and `stream_options`. [Pinned executor, request rewrite and POST](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_executor_execute.go#L18) | This is a real local compatibility transformation, but it is not a local Responses-object database and does not demonstrate HTTP `previous_response_id` semantics. The submitted `input` remains the caller-provided/reconstructed history; an executor helper separately handles cached reasoning replay. Do not infer full transcript recovery from deleting the ID. A local adapter can do the same kind of request normalization; full ID-based retrieval needs either upstream state or an explicitly implemented complete local store/replay design. |
| WS continuation / HTTP-to-WS bridge | The auto executor selects upstream WS only if the *downstream* request is WS and the selected auth enables WS. HTTP always uses the legacy HTTP executor; if WS is required but cannot be reused, it returns a replay-required error. WS executor documents HTTP fallback for operations unavailable over WS, including compact. [Pinned WS routing and fallback](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_websockets_executor.go#L529) | CPA is not an HTTP-to-WS continuation bridge. Its native WS session path is an example for session-sticky transport and connection reuse; it is distinct from the HTTP `previous_response_id` failure. This matches our passing native WS test, not the failing HTTP test. |
| ID-to-credential affinity | A public feature issue states the session selector did not map a bare `previous_response_id` to the auth that created it; provider-owned IDs can fail if the next request selects a different credential. The issue has no linked implementation PR in its public development block. [Issue #4640, problem and acceptance criteria](https://github.com/router-for-me/CLIProxyAPI/issues/4640#L165) | Even with the WS connection path, multiple OAuth accounts require affinity. This is an implementation detail that can be fixed locally with bounded ID→session/auth affinity; an upstream-owned ID cannot be safely rebound to a different account. Since the issue page is closed but exposes no code link, treat it as corroboration; the pinned executor and route source remain primary. |
| Reasoning and replay cache | The HTTP executor calls `sanitizeOpenAIResponsesReasoningEncryptedContent`, then `applyCodexReasoningReplayCacheRequired`; after a successful completed response it calls `cacheCodexReasoningReplayFromCompleted`. [Pinned calls](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_executor_execute.go#L57) | This is a proxy-local **reasoning-item replay cache**, not proof of a complete prior-response store or of prompt-cache hits. It can preserve/repair reasoning replay inputs, but cannot mint valid upstream-encrypted content or prove the upstream will emit `encrypted_content`. Our missing `encrypted_content` result remains provider/account/request dependent unless the request/response transformation is shown to be wrong. |
| Legacy compact path | The HTTP handler has a separate Compact operation; it removes `stream` and dispatches `Alt=responses/compact`. The Codex executor sends that operation to `baseURL + /responses/compact`. Default `baseURL` is `https://chatgpt.com/backend-api/codex`; custom Codex API-key configs may set another URL. [Pinned handler](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/sdk/api/handlers/openai/openai_responses_handlers.go#L3204), [pinned Codex upstream URL](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_executor_execute.go#L196) | This is endpoint forwarding, not local compaction. It will only work if the configured upstream implements `/responses/compact`. It does not establish the newer v2 protocol (`POST /responses` with `input[].type=compaction_trigger` and a required `compaction` output item). An Aug 8 report against 7.2.121 recorded that the ordinary Codex path did not preserve/guarantee that item; use as a versioned limitation signal, not as proof about every post-pin release. [Issue #4848 protocol distinction](https://github.com/router-for-me/CLIProxyAPI/issues/4848#L316) |
| Web search / aliases | The audited Codex execution path translates the request, normalizes Codex tool schemas, and sends `/responses`; the executor has no explicit `web_search` / `web_search_preview` alias mapping. A separate `POST /v1/alpha/search` route exists. [Pinned request path](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_executor_execute.go#L42), [separate route registration](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/api/server_routes.go#L55) | No evidence that CPA rewrites a Responses `web_search` alias into its own search service. Native search is upstream/model behavior; `/alpha/search` is a separate endpoint, not an alias bridge. Current v7.3.1 release notes later added per-model web-search capability metadata for the catalog; that can advertise which models support search but does not itself execute or translate the tool. [v7.3.1 release note](https://github.com/router-for-me/CLIProxyAPI/releases) |
| Images | The normal Codex request goes to the configured upstream `/responses`. Separately, `codex_openai_images.go` adapts `/v1/images/generations` and edits into Responses image-generation calls and extracts `image_generation_call` output. [Pinned executor](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_executor_execute.go#L42), [pinned image path](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_openai_images.go#L79), [image edit input conversion](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/runtime/executor/codex_openai_images.go#L458) | Generated-image API support is real code, but it is not evidence that the proxy locally understands arbitrary input images. Ordinary vision semantics remain upstream/model-dependent. If our PNG request payload was malformed/dropped, translation is fixable; if the upstream received it and answered “beige,” the proxy cannot improve model perception by itself. |

### Locally routed surfaces versus upstream-only behavior

At this SHA, server routes register `GET/POST /v1/responses` (the GET is the WS upgrade), `POST /v1/responses/compact`, and `POST /v1/alpha/search`. There is no registered Responses `GET /{id}`, `DELETE /{id}`, `POST /{id}/cancel`, `/input_items`, `/input_tokens`, or `/conversations` route. [Pinned public route table](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/internal/api/server_routes.go#L55). The handler source likewise separates ordinary Responses from Compact and has no lifecycle operation in this path. [Pinned handler](https://github.com/router-for-me/CLIProxyAPI/blob/09a29bd345bc44c473abe7fd07859e32df2ea543/sdk/api/handlers/openai/openai_responses_handlers.go#L3151).

Consequences:

- Retrieve/delete/cancel/input-items and Conversations CRUD are not locally implemented by this Responses surface; direct requests hit no matching route. Do not describe these as “forwarded to paid OpenAI.”
- `input_tokens` has an internal `CountTokens` executor method, but no public Responses input-token route at this SHA. An internal method is not an exposed API.
- `background` has no local async job registry or poll route in the listed surface. If retained through generic translation, any behavior belongs to the configured upstream; it is not a CPA-managed background job.
- Ordinary generation defaults to the ChatGPT Codex backend URL under Codex OAuth. If a user configures a custom Codex API-key base URL, generation follows that URL instead. Neither mode creates missing local lifecycle routes.

## Fixability summary

- **Good local fixes:** deterministic request normalization; public lifecycle routes backed by explicit storage; a proper HTTP state store or complete history replay; response-ID-to-auth affinity; alpha/native search routing with explicit alias policy; stronger input-image payload tests; capability/error reporting.
- **Needs upstream support or an intentionally new local feature:** actual `previous_response_id` state owned by OpenAI; valid encrypted reasoning blobs; provider-native web search; vision answer quality; true upstream background polling. A proxy can preserve or translate these contracts only when the target supports an equivalent operation, or when it deliberately owns the missing state/operation.
- **CPA evidence is not a pass for our failures:** its successful WebSocket continuation is transport-specific, its Compact route is routed upstream, and its reasoning cache is narrower than full Responses persistence. It offers implementation patterns, not a drop-in source for every failing scenario.
