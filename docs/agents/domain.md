# Domain docs

This repository has one domain context.

- Before exploring domain behavior, read root `GLOSSARY.md` and relevant decisions under `docs/adr/`, when present.
- If absent, proceed. Create glossary terms and ADRs lazily through `domain-modeling`, only when terminology or a consequential trade-off is actually settled.
- Use the glossary's canonical terms in specs, tickets, tests and reviews.
- Surface conflicts with an existing ADR before changing the affected behavior.
- Existing reports and proposals retain their dates and qualifications. Recheck their sources before treating them as current implementation or accepted requirements.
